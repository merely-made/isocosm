## Why

structure that itself creates internal relations that cue related context."
And, asked who assigns keys: "I don't mind relinquishing the explicit
numbering if when I say something it doesn't become a chit on a pile of
chits. If my judgment calls or deference to your recommendations helps feed a
stack doctrine that doesn't grow endlessly, but refines itself over time and
successfully relates the relevant rulings to prior judgment to determine the
most efficient technical architecture for our goals and stack…. That would be
my true goal."

The design record already meant to have two layers. §0 calls its cases
"precedent the later sections derive from", and §1 to §11 are that derived
design. The derived layer stopped keeping up:

- 984 cases since 2026-09-17, about 30 a day (some 340 dated in September,
  520 in October). 743 are live; 216 operational or replaced cases moved to
  the archive by hand on 2026-10-18.
- §1 to §11 (3,860 lines) cite 214 distinct cases. The other live cases reach
  no derived statement; they exist only as entries.
- `case_register.md` groups the live cases into 17 areas, one line each; 213
  rows cite no plan.
- 760 code comments in 308 `.rs` files cite rulings, one way: nothing lists
  the code a ruling governs.
- Relations between cases are prose: 23 places say "amended by",
  "supersedes" or the like.
- `DOC_README.md` holds 20 working principles, which read as doctrine
  already.

So context arrives only when someone remembers it, and every answer adds an
entry whether or not it said anything new.

## Design

### Two layers

- **Doctrine** is what is read. One document, by the register's areas, of
  short statements, each citing the cases it rests on. It is the current
  answer to "what do we hold, and why".
- **Cases** are evidence: Mark's words as given, kept, linked, and read when
  a statement's grounds are in question, not during ordinary work. The
  record's §0 becomes the case archive behind the doctrine. §1 to §11 are
  absorbed into doctrine area by area during the backfill, then archived.

### How an answer touches doctrine

Every question put to Mark names the statement it bears on, from the lookup,
and a recommendation names the statement it applies. Each answer is recorded
as one of four outcomes:

| Outcome | When | Doctrine |
| --- | --- | --- |
| applies | the answer follows from a statement, including taking a recommendation that applied one | unchanged; the case is filed under the statement |
| refines | the answer sharpens or narrows a statement | the statement is rewritten; its old text goes to history |
| contradicts | the answer pulls against a live statement | a fork back to Mark before anything is written |
| new | no statement covers it | a statement is added |

Only *new* grows the doctrine. An operational answer (merge, push, which run
to accept) is not a case at all; it lives in the commit message, as now.

Each area has a size budget, set by Mark. An area over budget gets a
consolidation round: merges and retirements put to Mark as cards.

### Keys

- Cases keep their numbers; the 743 live numbers and their code citations do
  not change. New cases take keys mechanically, in answer order.
- A plan's decisions take plan keys, `sim-execution D3`, cited the same way
  in code. One that another plan or the code comes to rely on is promoted to
  a wing key; the plan entry keeps its key and gains `promoted`, and the
  lookup resolves both.
- Doctrine statements take stable keys within their area, so a statement can
  be rewritten without its citations moving.

### Links

Each case and each statement carries one fields line. Illustrative, not a
fixed syntax yet:

```text
Links: area Execution · draws on 975, 338 · plans sim-execution · governs shared/isocosm/src/stage/mod.rs Stage
```

| Link | Means | Kept by |
| --- | --- | --- |
| area | one of the doctrine's areas | judged |
| draws on | precedent it rests on | judged |
| amends | changes part of an older decision; both stay live | judged |
| replaces | the older text moves to history | judged |
| contradicts | two live decisions pull against each other; neither amends | judged, and put back to Mark |
| plans | the plans that carry it out | judged |
| governs | code paths or symbols it rules | judged |
| stack | the statement concerns the stack, not only the wing | judged |
| mentions | keys in its text | generated |

Generated in reverse: drawn on by, amended by, replaced by, contradicted by,
cited in code. A case filed under a statement is a link of its own (*under*),
written when the outcome is recorded.

### Manifest, register and lookup

- `decisions.toml`, generated from the fields lines, the texts' mentions and
  the code's citations. Nobody edits it. The pre-commit hook regenerates and
  stages it when a design doc or a citing source file is staged, beside its
  line-ceiling and pack checks.
- `case_register.md` is generated from the manifest: each case's one-line
  summary moves into its fields line.
- One lookup command answers: what governs this path or symbol; this
  statement's or case's neighbourhood; this area's doctrine. Lane briefs and
  questions to Mark quote its output.
- The anchor check runs when a consolidation round is prepared, not per
  commit: rust-analyzer's SCIP index of each crate a `governs` link names,
  read by a small reader in `scripts/`, every anchor looked up by qualified
  name. A statement whose anchors are all gone enters the round as
  obviated; a moved anchor is rewritten to its new place.

### Shaped for the stack

Statements tagged *stack* (mere, genet, netrender, formats, the build) are
the candidates for a stack-level doctrine in mere's `design_docs/` once the
shape works here. Going global then means Mark's `CLAUDE.md` and the other
repositories' doc policies, each text approved by him.

## Implementation

- **L1. The rule.** The two layers, the four outcomes, keys, link types and
  the fields line written into `design_docs/DOC_POLICY.md`'s local addendum.
  Done when Mark approves the text.
- **L2. Generator, manifest, register, lookup.** A script in `scripts/`
  parses fields lines across the wing's design docs, mentions in their text,
  and code comments; writes `decisions.toml` and `case_register.md`; answers
  lookups. The hook calls it. Done when both regenerate byte-identical twice,
  the hook stages them on a staged doc change, and the lookups for 975 and
  `stage/mod.rs` return what the record and code say. The anchor check
  passes the probe's answer key (2,511 definitions from git history) and
  finds `Effect::Sunlight` and `Receipt.foregone`.
- **L3. The mechanical layer.** Every live case gets its area from today's
  register; mentions and code citations are generated. Done when all 743
  cases carry an area and the manifest's citation count matches a grep.
- **L4. Doctrine by area.** Per area: a lane drafts the area's statements
  from its cases and from the matching parts of §1 to §11, files every case
  under a statement or flags it, drafts the judged links, and lists each
  *contradicts* it finds. The draft goes to Mark as a card round; his answers
  are recorded with their outcomes. Done when all 17 areas are reviewed, each
  within its budget, and §1 to §11 are archived.
- **L5. The held six.** The execution plan's four 2026-10-19 answers and A
  and B entered under their plan keys, each recorded with its outcome against
  the Execution area's doctrine. Done when the lookup for `sim-execution`
  shows them.
- **L6. Global.** When L1 to L5 hold: stack-tagged statements moved to a
  stack doctrine in mere, and the rule carried into Mark's `CLAUDE.md` and the
  other repositories' doc policies, with his approval of each text.

## Findings

- **2026-10-20, the existing pieces** (counted, not built): 743 live cases in
  17 register areas; 213 cited by no plan; §1 to §11 cite 214 distinct
  cases; 760 code citations in 308 `.rs` files; 23 typed cross-references in
  the record's prose; 20 working principles in `DOC_README.md`. The hook is
  `.githooks/pre-commit`, calling PowerShell scripts under `scripts/`; the
  600-line ceiling covers `.ps1` and `.py`.

- **2026-10-20, what the stack supplies** (read, not run). Mark passed on
  another session's take, "not the correct approach, but using the stack
  seems wise", so its pieces were checked against the tree:
  - `wing-impresa` (`shared/wing-impresa/src/impresa.rs:44`): one `Record`
    of subject, object, kind, canon revision, cause, tick and a `Stance` of
    associate or lapse; "a lapse is a record", never a deletion; ids are
    opaque `namespace:local` strings and kinds a configured `KindSet`, so
    `case:975`, `plan:sim-execution` and a doctrine statement fit unchanged.
    Its canon revision ("what a kind meant then is not necessarily what it
    means now") is the doctrine revision a link was made under. Default
    limits, 65,536 entries and 8 MB of JSON, hold the roughly 5,000 links
    743 cases and 760 citations make.
  - `muniment`, the append-only journal: no longer in mere's tree. It moved
    to `merely-made/eidetic` (`repos/eidetic/crates/muniment`); mere pins it
    by git rev. Mere's `crates/eidetic/README.md` still describes it as
    there.
  - The reach field (`shared/isocosm/src/reach.rs`): strength fading by
    `decay_per_tick` to a `legend_floor`; legends do not fade. The formula
    lives inside the sim.
  - The hagiograph's feat rule (`repos/eidetic/crates/hagiograph/src/
    reckoning.rs:30`): an entry is a feat when it beats a mark that stood
    before the batch. It judges high-water marks on an axis.
  - sem, for checking that a `governs` anchor still exists.
  - The citation scanner the take names was not found under `scripts/`.
- **2026-10-20, the anchor instruments compared** (run on `shared/isocosm` at
  `afbce8a0`; report and receipts in
  `Code/testing/isometry/anchor-probe-2026-10-20/`). Mark: "compare the
  rust-analyzer approach to what would be required of sem". Against a key of
  2,511 definitions from git history (472 kept, 248 moved, 1,791 removed),
  rust-analyzer's SCIP index, sem and a plain definition regex were each
  right on every one. On today's methods by owner, SCIP and sem agree on
  1,274 of 1,277. They part on reach and cost: SCIP sees enum variants (730)
  and fields (3,228), which sem does not list, so `Effect::Sunlight` or
  `Receipt.foregone` are checkable only by SCIP; SCIP resolves aliases and
  macros, sem reads spelling; SCIP takes 120 s and 40 MB a run, sem 0.4 s.
  174 of 1,602 top-level names and 135 of 948 method names are defined more
  than once, so anchors are qualified (module path, owner). A move changes a
  SCIP symbol (it carries the impl block's module), so either instrument
  relocates an anchor by qualified name. rust-analyzer comes with the pinned
  toolchain; its `scip` subcommand is marked unstable, its format is not.
  Mark then recovered the 2026-10-15/16 record: Mergiraf 0.20.0 was the
  alternative trialled, as a merge driver replacing weave, not as a lookup
  tool. It was installed by Homebrew on the Mac, registered globally there,
  and enabled only in that machine's `mere/.git/info/attributes` (Rust,
  TOML, JSON, YAML, Markdown); only installation and `git check-attr` were
  checked, no merge-fixture comparison. No evaluation of sem as an
  instrument was found. On this Windows machine, checked the same day: no
  `merge.conflictStyle`, no `rerere`, no Mergiraf in git config, so the
  "zdiff3 + rerere" settings the record calls global are the Mac's only.
